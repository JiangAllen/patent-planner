# 簡報素材總覽（從這份開始看）

鴻海二面（2026-10-16）20 分鐘簡報的基礎。所有數字都已核對過 `reports/scored/`，可以直接使用。

## 1. 一句話

用合成資料對 4B 模型（Qwen3-4B-Instruct-2507）做 QLoRA，讓它當專利答辯 Agent 的 Planner。微調後：
- 熟題型從 61% 進步到 99–100%。
- 沒看過的題型從 21% 進步到 44%；第二輪補資料後再升到 54%。

結論：在本實驗中，模型能把部分學過的元件重新組合，但未能可靠產生訓練資料沒示範過的參數用法或輸出形狀。主成果以 v1（44%）為準；v2（54%）是看過 OOD 失敗原因後的針對性調整，用來驗證錯誤分析，不是無偏的泛化成績。

## 2. 答對題數（主指標 plan exact match，整份計畫全對才算 1 題）

| run | 熟題型 test_id | 沒看過題型 test_ood |
|---|---|---|
| zero-shot | 50 / 121（41%） | 31 / 149（21%） |
| few-shot | 74 / 121（61%） | 32 / 149（21%） |
| qlora-r16 | 120 / 121（99%） | 66 / 149（44%） |
| qlora-r16-v2 | 121 / 121（100%） | 81 / 149（54%） |

配對檢定（同一批題目逐題比較）：
- v1 對 few-shot：OOD +0.228 [+0.161, +0.295]
- v2 對 v1：OOD +0.101 [+0.040, +0.161]

兩組差異的信賴區間都不包含 0：在這批題目上，抽題的隨機性解釋不了這個差距。但要誠實說明兩點：(1) 每組只訓練一次，沒有涵蓋重新訓練（seed）的變異；(2) OOD 實際上只有 6 個結構，v1 的 44% 主要來自 S10（25/25）與 S17（23/25）。

## 3. 輔助指標（test_ood）

| run | schema 合法 | action 準確 | tool F1 | 誤用干擾工具 ↓ | 字面參數 | 引用參數 | 相依 |
|---|---|---|---|---|---|---|---|
| zero-shot | 0.826 | 0.664 | 0.727 | 0.280 | 0.705 | 0.353 | 0.430 |
| few-shot | 0.899 | 0.638 | 0.760 | 0.270 | 0.846 | 0.433 | 0.590 |
| qlora-r16 | 0.993 | 0.953 | 0.920 | 0.170 | 0.948 | 0.520 | 0.690 |
| qlora-r16-v2 | 0.993 | 0.973 | 0.914 | 0.220 | 0.942 | 0.693 | 0.760 |

怎麼解讀：
- 所有輸出都能解析成 JSON（1.000），schema 合法是更嚴格的格式檢查。
- 工具選對（F1 0.92）、字面參數填對（0.94）、要不要動作判斷對（0.97），都已經很高。
- 最弱的是**引用參數**（0.52 → 0.69）與**相依關係**，也就是「把上一步的哪個結果接到下一步」。這是剩下失敗的主因。

熟題型的完整數字（全部接近 1.0）見 `reports/results.md`。

## 4. 簡報故事線（建議）

1. **問題**：專利答辯需要多步驟工具呼叫，Planner 要輸出可執行的 DAG。→ `docs/design.md`
2. **資料**：30 個模板反向生成，再用 LLM 改寫；6 種結構只放在 OOD 測試集，訓練時完全看不到。→ `docs/design.md`、`data/manifest.json`
3. **Baseline**：few-shot 讓熟題型進步，但 OOD 沒進步；而且 OOD 的拒絕題從 80% 掉到 0%：示範中的拒絕是「完全沒有相關工具」，OOD 的 S30 是「只缺一個工具」，模型被帶向產出 plan（test_id 的拒絕反而上升，所以只限 OOD）。
4. **QLoRA**：熟題型幾乎全對，OOD 翻倍。→ `reports/figs/exact_by_category_test_ood.png`
5. **Error analysis**：失敗集中在 3 種結構。原因是訓練資料缺某些元件（例如答辯書從不帶修正內容）。→ `reports/error_analysis.md` 第 1–5 節
6. **第二輪驗證假設**：補元件後元件學會了（0/25 → 16/25），但組合與兩跳推理沒有轉移。→ `error_analysis.md` 第 6 節、`docs/plan-v2.md`
7. **Demo**：一句話 → 計畫 → mock 工具依相依執行；另示範追問與拒絕。附帶發現：zero-shot 在 test_id 有 95 份計畫跑得完，其中只有 35 份正確——「不報錯」不等於「做對」，所以要對照 gold 評估。注意 demo 的三句話接近訓練模板，只用來展示流程，不當作推理能力的證據。→ `reports/demo.md`
8. **限制與下一步**：見第 5 節。

## 5. 一定要主動講的限制

1. 熟題型 99–100% 代表題目太簡單（與訓練資料同模板），只能證明格式學會了；重點看 OOD。
2. 全部是合成資料，沒有在真實請求上驗證過。
3. 每組只訓練一次（單一 seed），不知道重新訓練的波動有多大。
4. 評分很嚴格：把引用寫在句子裡就算錯。放寬後 v1 的 OOD 是 0.517、v2 是 0.617（`evaluation/sensitivity.py`）。
5. 熟題型的 clarify 只有 4 題，所以 clarify 改用合併的 n=28 報告。
6. v2 是看了 OOD 的失敗原因才補資料，54% 偏樂觀。
7. 改寫有約 2% 的錯字（「答辨」）。刻意保留，當作真實使用者的雜訊。
8. 改寫品質：自動守門只保證 slot（案號、日期、指示文字等）逐字保留，不通過就退回原句；slot 以外的用字不受保護。人工逐筆標記 90 筆：✅ 78、⚠️ 6（錯字、贅詞）、❌ 6（術語偏移或錯置 4、混入無意義英文 2）。全資料集掃描：混入英文雜詞 0.9%、專利號被稱為案號 2.4%、錯字 2.2%（`reports/spot_check.md`）。
9. 統計：配對 bootstrap 只涵蓋抽題變異，沒有涵蓋 seed 變異；OOD 以結構分群，只有 6 個結構，理想上應以結構為單位計算 CI。
10. S26（clarify）只接受一個正確的缺漏集合，部分「失敗」在語意上也合理，屬於標註設計的限制。
